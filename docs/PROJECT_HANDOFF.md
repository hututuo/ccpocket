# CC Pocket 项目交接手册

> 本文是长期协作原则和产品约束，不是版本状态、任务进度或发布记录。
> 接手具体任务时，仍须重新核对当前源码、分支、运行中的 Bridge、安装包和真机状态。

## 1. 项目目标

CC Pocket 的目标不是在手机上重新实现一个独立的 Codex，而是提供一个可靠的远程控制与阅读界面：

- 电脑上的 Codex / Claude 及其官方 app-server、CLI 和持久化记录仍是会话事实来源。
- Bridge 负责连接代理、统一协议、恢复历史、同步状态、做兼容转换和承载适合后端更新的能力。
- Mobile 负责交互、渲染、本地缓存、离线体验和 iOS 原生能力。
- 手机和 Codex Desktop 应尽量呈现同一个会话、同一种状态和同一套配置，而不是两个各自推测的副本。
- 用户希望自己的 `owner` 设备可以频繁更新；其他人的 `stable` 设备只接收阶段性确认过的版本。

产品优先级依次是：

1. 会话和数据正确；
2. 新旧版本兼容；
3. 官方更新容易合并；
4. 性能和长期稳定；
5. 与 Codex Desktop 一致且适合手机的交互；
6. 视觉细节。

不能为了最后一项破坏前面的任一项。

## 2. 接手任务前必须做什么

开始修改前：

1. 阅读仓库根目录的 `CLAUDE.md`、本文和 `decisions.md` 中与任务相关的章节。
2. 在本机工作区工作时，先读工作区根目录的 `AGENT_ERROR_INDEX.md`，命中触发条件后再读对应详细建议。
3. 确认真实源码仓库、绝对工作树路径、当前分支、起始基线、远端和 `git status --short`。
4. 确认是否有其他 Agent 正在修改相同文件。多 Agent 共享文件系统，所谓“只读 Agent”并不等于物理隔离。
5. 对运行问题，先确认正在运行的二进制、PID、监听端口、日志、手机连接目标和版本；不要从旧文档或屏幕历史推断当前状态。
6. 对会话问题，先做跨层只读取证，不要先重启服务、清缓存、删除数据库或重写会话。

如果当前工作树含有他人未提交改动，应新建独立 worktree。`git worktree add` 的目标必须使用绝对路径。

## 3. “兼容和独立”的准确含义

用户所说的“独立”主要是：

- 官方代码和本地扩展各自有清楚的行为归属；
- 官方发布新版本时，可以理解双方改了什么，并在少量稳定接缝上做语义合并；
- 一个功能有聚合的提交、测试和兼容说明；
- 不把多个无关需求混成一个大补丁。

它不意味着每项功能都必须从最终 HEAD 机械地一次 `git revert` 并完全还原官方 tree。不要为了“可拆”制造多余的 adapter、foundation 和层层抽象。

推荐做法：

- 一个用户可感知行为对应一个内聚 commit；协议、原生宿主、Mobile 行为和文档可按真实依赖拆分。
- 新功能优先拥有自己的目录、状态和测试，但共享行为确实属于官方热点时，可以窄范围修改共享文件。
- `websocket.ts`、`bridge_service.dart`、会话 Cubit、消息模型、聊天列表、`main.dart` 和 Xcode 工程等热点只做必要 hunk。
- 不对官方热点运行会产生全文件变化的 formatter、codegen 或机械替换。
- 不散落大量 feature flag，不跨功能共享私有状态，不写含义模糊的“统一 hardening”大提交。
- 官方更新时先读上游变化，再保留双方语义；不要简单选 ours/theirs，也不要把整个本地分支当黑盒 patch 重放。

每个跨版本功能至少说明：

- 行为 owner；
- 与官方代码相交的接缝；
- Bridge / Mobile / native 的依赖顺序；
- 旧 App、新 App、旧 Bridge、新 Bridge的兼容矩阵；
- 未知未来字段和不支持能力如何降级；
- 回归测试覆盖什么真实记录形状。

## 4. 权威数据与身份规则

### 4.1 会话事实来源

- Codex app-server、Claude 运行时和原始持久化记录是权威来源。
- Bridge 可以标准化、补全和转换，但不能凭标题、文本或 UI 状态发明另一套会话事实。
- Mobile runtime 和本地 Mirror 是缓存与呈现层；Mirror 必须可重建，不能反过来覆盖 canonical history。
- 不得把“手机列表里看不到”解释成“会话已删除”。

排查会话缺失或错乱时，应对照：

1. provider thread ID 和父子 lineage；
2. 原始 Codex JSONL / app-server 返回；
3. Bridge 的 session list、watch、history 和转换结果；
4. Mobile runtime；
5. 本地 Mirror / SQLite；
6. 当前项目路径、worktree 和分支。

未经证明，不删除或改写原始 rollout、Codex 会话文件和官方历史。

### 4.2 身份不能靠名字

- 会话、下载记录、常驻策略、自动审批和分支关系一律使用 durable provider thread ID，并在需要时加 Bridge/machine identity。
- 会话名、预览文本、相同回复内容和临时 runtime session ID 都不能作为唯一主键。
- 相同标题的两个会话必须保持独立。
- Fork 的父子关系使用 provider lineage 字段；父子共享继承前缀是正常现象，不能据此合并两条历史。

### 4.3 一套语义转换

实时流、Desktop 历史重建、完整会话下载和本地 Mirror 必须尽量复用同一套消息/工具语义分类：

- 官方结构化事件优先；
- 原始 rollout 只补官方 API 遗漏；
- 用 call ID 和语义等价规则去重；
- 未知未来类型保留 generic fallback，不静默丢弃；
- Mobile 负责稳定类型、本地化和显示，不在客户端从任意 shell 文本重新猜权威工具类型。

## 5. Bridge 优先与版本化 Mobile Host

### 5.1 能在 Bridge 解决的，不要无故要求重装 IPA

以下能力优先放在 Bridge：

- provider 协议漂移；
- session 状态、排队、引导和运行时所有权；
- live/history/Mirror 的统一转换与去重；
- 会话 lineage、工具类型和模型目录提取；
- 旧客户端可消费的兼容下转换；
- 后台自动审批等电脑端持续执行的策略。

以下能力通常属于 Mobile：

- 新的可见交互和布局；
- 本地数据库分页与离线缓存；
- iOS Quick Look、分享、文件选择、通知、定位等原生能力；
- 必须引入新 wire contract 的客户端功能；
- 动画和设备端性能。

“后端优先”不是把所有逻辑硬塞进 Bridge；它是为了减少不必要的手机重新签名，同时保持清晰的协议边界。

### 5.2 App 是版本化宿主，不是远程网页壳

- App 和 Bridge 仍按版本发布。
- 后端不得下发任意 Dart、Swift、JavaScript 或可执行代码。
- App 可以预置一组有版本的原生/Flutter primitives，由能力协商决定是否展示和调用。
- 未知组件、动作、权限或 schema 版本必须 fail closed，并提示需要更新基础 App。
- 配置和补丁下载后保存在本地，重开后运行；不要每次启动都依赖重新读取一套动态页面配置。

### 5.3 更新边界

- Bridge 协议与后端逻辑可以独立部署，但必须兼容旧 App。
- 纯 Dart 代码可在已验证的个人 Shorebird app 上走 OTA。
- Swift、插件、entitlement、原生依赖、Flutter engine、Xcode 配置和需要打包的新原生资源必须发布新的基础 IPA。
- `MobileHostSnapshot` 和 capability table 使用可选、可加字段；不能仅比较一个总版本号来假定全部能力存在。
- 权限状态可以读取，但任何系统授权提示只能由明确的用户动作触发，不能在启动、恢复或加载配置时自动弹出。

## 6. owner / stable 发布制度

- 普通设备固定使用 `stable`。
- 用户自己的设备使用 `owner`，可以频繁接收测试补丁。
- `owner` 验证通过后，才能把指定补丁晋级 `stable`；stable 用户无需依次安装中间 owner 补丁。
- 从 owner 切到 stable 只影响未来检查，不伪装成立即降级。
- stable 出问题时使用受控回滚或发布更高版本修复，不在客户端偷偷改版本状态。
- 上游文档或脚本若仍使用 `staging`，不能据此擅自改变本地策略；先核对当前个人 Shorebird app 和发布脚本，兼容 fork 的长期通道名称是 `owner` / `stable`。
- 普通用户看不到随意切换 owner 的入口；本机开发者通道通过版本号连续点击七次解锁，解锁和通道保存在安全存储。
- 软件更新设置支持自动、静默和手动三种策略。手动“检查更新”绕过自动检查节流，但发现更新后仍需第二个动作才下载。
- 更新界面显示基础版本、构建号、当前 patch、通道、检查时间、下载进度、待重启状态和可理解的失败原因；发现更新或等待重启时设置入口显示提醒。

必须把以下状态分开汇报：

1. 源码已实现；
2. 提交已集成；
3. Bridge 已构建；
4. Bridge 已部署并通过实时协议检查；
5. App 测试通过；
6. 模拟器构建成功；
7. IPA 已生成并通过包结构/架构/签名检查；
8. IPA 已经 AltStore/AltServer 签名安装；
9. 真机已启动并完成行为验收；
10. owner 补丁已发布并在真机重启后生效；
11. stable 已由用户明确批准并晋级。

前一项不能替代后一项。“ready”“构建成功”或模拟器截图不是发布完成。

## 7. 会话同步与运行状态

### 7.1 Desktop 与手机必须是同一状态

- Desktop 发出的用户消息、运行状态、流式正文、工具调用、问题和完成状态，应同步到手机。
- 用户不应必须打开某个会话页面后才开始接收。已经激活且正在运行的会话，应由 Home 的有界 watcher 保持同步。
- 打开会话时，把 watcher 所有权转给会话页，排空有界 backlog，再做 canonical reconciliation。
- 正在运行不等于禁止手机输入。手机应支持与 Desktop 一致的排队、修改/取消排队和 steer/guide 能力；不支持的旧 Bridge 路径再明确降级。

### 7.2 重连与旧数据

- 每次 Bridge 重连都有新的 generation。旧 session list、capability、watch ack 和延迟帧不能重新取得当前所有权。
- 同目标重连后，要等新一代权威 session list 再恢复 watch。
- timeout 和重试必须有上限；路径不允许等结构性错误不能无限重试。
- 前台恢复先恢复交互协议和 watcher，再做按序号/身份的增量对账。

### 7.3 完整会话与渲染窗口

- 完整下载表示本地拥有耐久副本，不表示 Flutter 一次挂载全部消息。
- 默认设计上限是每会话 100,000 个 normalized entries / 64 MiB；普通会话页只挂载约 200 条可渲染 envelope。
- 更老记录按页或目标窗口读取。History 索引必须覆盖所有真实用户轮次，即使它们不在当前渲染窗口。
- 选择远距离历史轮次时，先显示加载状态，直接读取目标附近窗口，再跳转；不要把中间几千条全部挂载。
- 性能修复不能用更小的产品数据上限、静默截断、显示零值或 metadata-only 冒充。
- 大 JSONL、tool result 和 Mirror 数据使用流式/增量/分页读取，工作集有界，总历史不能因为工程实现方便而丢失。

### 7.4 常驻会话

- 常驻是现有会话 Mirror 的同步策略，不是新的 Codex session type。
- 运行中的会话也可以切换常驻；列表行和会话 More 菜单都提供入口。
- 常驻会话下载完整历史、在 Home 有独立分类，并在 App 运行且 Bridge 可用时自动增量更新。
- 打开常驻会话仍只挂载有界窗口，不能因为已经完整下载就一次渲染全部内容。
- 自动恢复的 watch 数量有明确上限；没有 durable provider ID 时可以等待权威身份，但不能保存猜出的临时 ID。

## 8. 会话 UI 的长期约束

### 8.1 两层折叠结构

中间过程必须是正确的数据和组件树，不是视觉上看起来像折叠：

- 一个历史回合只有一个外层“中间过程”容器。
- 每个临时 assistant 输出是一个内层 segment。
- segment 顺序固定为：可见临时文本 → “思考与执行”标签 → 属于该段的思考、工具和结果。
- 工具结果按 tool-use ID 回到发起它的 segment，即使结果晚于下一段文本。
- 最终回复保持在外层折叠之外。
- 当前正在生成的最新临时文本作为“当前进度/当前状态”显示在外面；其后只显示最新工具摘要，点开才看该进度段的详情。
- 计划/TODO 清单是独立的实时卡片，与当前状态同层；`update_plan` 之类的内部更新不应长期占据“正在使用的工具”栏。

展开必须在布局阶段保留用户点击的视觉锚点并向下铺开：

- 不能先闪到错误位置，再用 post-frame `jumpTo` 拉回。
- 长段、短段、reverse list、分页和另一轮正在流式输出都要测试。
- 工具详情、代码、参数和图片在折叠时不得构建、解析或下载；第一次展开后再按需加载。
- 箭头负责一次展开/一次收起；详情里的 Show more 只负责进一步展开，二者状态不能混用。
- 会话首次激活以及停用后重新激活时默认全部折叠；More 菜单提供“一键全部折叠”。

### 8.2 与 Codex Desktop 对齐

- 能复用完整会话页的地方不要另写简化聊天组件。持久 Side Chat 应复用普通 Codex 会话屏幕，并通过 capability 参数隐藏不支持的 Fork 等动作。
- 工具活动要覆盖 Codex 常见的读取、搜索、列文件、修改、命令、命令完成、Skill、子 Agent、等待/交互、Web 搜索、图片生成和压缩上下文等真实事件。
- 折叠态只显示“在做什么”、目标文件名和必要计数；具体命令、代码和大结果只在展开后显示。
- 文件修改完成的摘要默认显示文件名和修改行数，不直接铺开完整 diff。
- Codex Warning 等长期占位提示必须可关闭；可翻译的固定文案优先汉化。
- session start、配置恢复、reasoning effort 和内部 `continue` 等元数据主要用于恢复状态，不应反复生成占空间的 `System:` 时间线消息。
- Codex 引用图片时，手机应显示同一图片；折叠状态不得预加载大图。
- 选中文本可以加入当前会话或开启 Side Chat；两条入口复用同一选择接缝，不各自复制一套文本状态。

### 8.3 消息操作

- Fork 入口位于每条已完成 assistant 回复下方，与复制、分享同组。
- 会话正在运行时，早先已经完成的回复仍可 Fork；只有当前未完成的最新回复不可 Fork。
- reasoning、工具前言和中间 assistant update 不是独立完成回复，不能提供 Fork。
- live transcript 可能有 `ResultMessage`，Desktop 重建历史可能没有；完成判定必须同时覆盖这两种真实形状。

### 8.4 配置一致性

- 会话恢复时，从权威 session metadata 恢复模型、reasoning effort、service tier、sandbox 和 approval policy。
- 顶部工具栏和详情面板必须显示同一配置，不能外面正确、点开后又勾选 Default。
- 模型档位的 wire value 必须与 UI 一一对应，例如 light、medium、high、x-high、max、ultra；不能只改显示文本。
- 权限变更默认允许“下一轮生效”，并保留“立即重启会话”。Goal 的每一步边界可以应用下一轮策略，但不得打断当前正在运行的一步。
- 上下文额度圆环位于模型、Goal/计划和权限同一行的紧凑工具栏，不在右上角重复显示。点开后的详情保留“压缩上下文”动作。
- 若后端提供 5h/7d 额度、重置次数或重置时间，应显示权威值和来源；可以参考 Codex Token Bar 的读取方式，但不能从本地倒计时猜服务端配额。

## 9. 动画和视觉验收

- 如果用户给出参考仓库，先完整阅读其算法、状态、常量、坐标体系和许可证，再移植；不能看截图猜公式。
- 参考实现可合法复用时，隔离原算法、保留 SPDX/attribution，再做必要的平台适配。
- Max 和 Ultra 等语义、速度、配色、点击时间轴与持续火焰时间轴必须分别建模，不能用一个 elapsed 比例同时改变所有效果。
- 固定网格不能随滑块移动、伸缩或重新生成；滑块只改变前沿和可见 mask。
- 动画需要遵守 Reduce Motion、TickerMode 和生命周期释放，不能后台空转。
- 性能优化不能牺牲拖动即时反馈、尾流连续性或用户已经确认的视觉特征。
- 视觉和动态手感由用户最终验收。Agent 负责代码、静态几何/生命周期回归、性能证据和提供最新可运行构建；准备好后直接请用户看，不用昂贵且不可靠的自动截图反复替代用户判断。

## 10. 文件、预览与路径

### 10.1 文件链接与预览

- Codex 正常输出本地文件路径；Bridge 识别后转换为经过授权的 artifact reference，Mobile 渲染为可点击链接。不要依赖系统提示词要求模型手写某种私有 URL。
- artifact URL 只用于内容访问，不暴露任意本机路径。
- iOS 支持的网页内容优先 App 内嵌预览；Office/RTF 等复用经过验证的临时下载和 Quick Look。
- Flutter 拥有返回、下载、分享、隐藏、取消和文件落盘。关闭 Quick Look 后应回到“预览”而不是错误的“重试”状态。
- 预览页必须支持左滑/系统返回。

### 10.2 文件管理与传输

- 文件管理是 Home 一级入口，支持浏览电脑目录、固定常用文件夹、实时预览、下载到手机、手机上传电脑和接收文件 inbox。
- Mac 端 CLI 发送文件复用同一套可续传协议；电脑收到手机文件后落到明确的 Downloads 目的地，不能只存在临时缓存。
- 发送请求前先确认 iPhone/iOS 和 native host capability 支持，旧宿主 fail closed。
- 单文件传输上限默认 15 GiB；预览上限默认 2 GiB。
- 使用断点续传、校验、可取消流和自适应块大小。常见 1–10 MiB 文件不要固定使用 16 MiB 块；大文件再逐步增大。
- 不把大文件整体读进 Dart 内存；未知大小先检查空间，文件名按 UTF-8 字节安全清理。
- composer 中拖入文件表示上传后作为会话附件；拖到 Home 表示发给电脑，并显示清楚的放手发送反馈。
- 电脑发来的文件进入持久、可恢复、symlink-safe 的本地 inbox；用户可预览、分享、保存。
- 下载、常驻会话和文件索引使用唯一 ID，不按名称匹配。

### 10.3 路径安全

- Bridge 只能访问允许目录，错误要清楚指出路径授权问题。
- 所有路径经过统一 canonicalization 和 symlink 防逃逸检查。
- `/var` 与 `/private/var` 等 macOS 别名使用一致的规范化规则。
- Tailscale 是私有网络传输层，不是取消认证、allowed directories 和内容边界的理由。

## 11. 权限、自动审批和通知

### 11.1 权限

- 设置中可以提前展示宿主支持的权限管理入口，但只在具体功能需要且用户主动点击时发起系统授权。
- 读取状态与请求权限是两个动作。启动、恢复会话、下载配置和后台唤醒不能自动弹权限框。
- 未知权限 ID、旧 native API 或缺失 capability 都 fail closed，并提示需要基础 App 更新。
- 不为尚无真实功能的权限预先加入虚假 purpose string；确定未来会使用的能力，应在下一次基础 IPA 前一次性补齐真实宿主和说明。

### 11.2 自动审批

- 自动审批应尽量由 Bridge 按 durable Codex thread ID 持久管理，Mobile 是控制和审计界面。
- 手机断线不应让已明确托管的 Bridge 策略悄悄消失；反之，旧 Mobile 也不能在未显式开启时触发新 Bridge 自动审批。
- 两种来源的自动审批在 UI 上统一成紧凑卡片：外层显示已批准和风险级别，点开才显示具体命令/原因。
- 用户希望可以托管，但不等于隐藏风险。删除、破坏 worktree、插件安装、认证表单、模糊 shell 和用户问题仍应 fail closed 或人工确认。
- 设置中的 Disable all 必须始终可用；离线时要明确“等待发送”，不能假装远端已经关闭。

### 11.3 通知与后台

- 自签名 App 可以使用用户已授权的本地通知；不能把源码 entitlements 当成 AltStore 重签后 APNs/FCM 可用的证明。
- 设置页应区分需要操作、阶段进度、成功完成、失败等类型；中间过程默认可关闭并限流，避免刷屏。
- 如果采用“始终定位”维持自签名后台本地通知，它必须是显式实验性开关：
  - 不读取、保存、记录或上传坐标；
  - 只在有运行任务时启动；
  - 后台不解析和渲染流式正文，不跑 history、Mirror、文件同步；
  - 只接收轻量通知 envelope；
  - 低电量、严重温控、任务结束、权限丢失和长期断线时停止；
  - 回到前台先恢复 interactive，再增量追平。
- 这项窄用途是对早期“不得用定位延长后台”的唯一例外；不得把它扩展为后台同步正文、隐藏系统定位指示或请求精确坐标。
- iOS 仍可能终止进程，用户 force-quit 后不能承诺继续。不要把该方案描述成 APNs 的等价替代。

## 12. Goal、计划和运行控制

- Codex app-server 是 Goal 的唯一事实来源，不另建 Mobile Goal 数据库。
- Goal 的开启、暂停、恢复、修改、预算和删除使用官方或版本化的 Bridge RPC。
- Goal 变化在步骤边界生效，不凭手机 UI 猜测已中断当前步骤。
- 计划/TODO 清单在会话外层实时更新，已完成项目立即打勾；不要每次更新追加一张重复的静态卡。
- 权限重启、Goal 暂停/恢复和普通 turn continuation 必须有严格 lease，不能把被清除或替换的 Goal 误恢复成普通对话。

## 13. 性能原则

- 性能问题先测真实大历史、真实运行 App 和目标设备，不只看小 fixture。
- 隐藏内容不构建、不解析、不取图；滚动列表只挂载可视附近内容。
- 高频流更新要合批并保持最新进度可见，不能因为“优化”让实时反馈消失。
- 所有读取设工作集、页大小、字节和并发边界，但不能以丢历史为代价。
- 后台不做前台 UI 的流式刷新；回来后增量对账。
- 同一构建目录的 Flutter、Xcode、测试和打包命令串行运行；需要并行必须使用独立 cache/DerivedData。
- 开始大构建或打包前检查磁盘空间；完成后清理本轮可重建且已被替代的 build、Pods、`.dart_tool`、DerivedData、dist 和临时展开目录，源文件和唯一证据除外。

## 14. 多 Agent 与 Git 工作方式

### 14.1 物理隔离

- 每个会写代码的 Agent 使用独立 worktree 和独立分支。
- 只读审查和实现会触及同一文件时，也应错开时间或使用独立 worktree；prompt 中写“不要修改”不是隔离。
- 创建 worktree 前确认目标不存在；创建后核对绝对 top-level、分支、HEAD 和状态。
- 不在源码 worktree 内用相对 `_keep/...` 创建项目记录。

### 14.2 授权边界

除非用户或协调 Agent 明确授权，不得：

- 合入共享、集成或稳定分支；
- push、tag、发布 npm、发布 Shorebird、晋级 stable；
- rebase 或改写他人历史；
- 替换运行中 Bridge、重载 LaunchAgent；
- 安装或重签 IPA；
- 删除分支、worktree、会话数据和他人改动。

代码实现授权不自动包含部署授权，部署授权不自动包含 stable 发布授权。

### 14.3 提交

- 按行为/维护单元提交，不按聊天轮次提交。
- 探索性保存点用 `checkpoint:` 或中性描述，不能提前写“修复完成”。
- 提交前检查 status、cached diff、secret、大文件和构建产物。
- 强制检查使用 fail-fast；不要让后面的成功掩盖前面的失败。
- 不使用 `git add .` 收进未知文件，不使用 destructive reset 清理脏树。
- 合并前由协调 Agent 审核 commit 顺序、依赖、热点冲突、测试证据和兼容矩阵。

### 14.4 Agent 成本与自动化

- 可程序化的重复发布、检查和打包流程应先人工跑通一次，再逐步脚本化。
- 脚本负责确定性的命令、哈希、结构和状态检查；模型负责语义合并、冲突判断、风险分析和异常处置。
- 例行工作可交给较低成本但足够可靠的持久任务；官方更新、交错冲突、会话正确性和发布门禁仍由高能力 Agent 审核。
- 不为了省 token 降低合并、签名、真机或数据安全标准。
- Worker 完成后直接向协调任务回报，不要求用户人工转发，也不要无意义轮询或催促。

## 15. 验证标准

### Bridge 改动

- TypeScript build；
- 相关定向测试；
- 足够广的 Bridge 回归；
- old/new Mobile capability 行为；
- 真实 WebSocket request/ack/error；
- 若涉及会话，验证 live、Desktop history、Mirror 和 reconnect。

### Flutter 改动

- `flutter analyze` / 项目约定静态检查；
- 定向单元与 Widget 测试；
- 涉及共享消息模型时运行更广回归；
- iOS Simulator 编译；
- 不把模拟器构建等同于真机验收。

### iOS 原生改动

- plist 与本地化 lint；
- Xcode/Flutter iOS 构建，日志默认使用 quiet/摘要，避免泄露环境；
- native capability 和旧宿主 fail-closed 测试；
- 生成新的基础 IPA；
- 真机授权、启动、后台、Quick Look、分享、文件和功耗验收。

### 会话与历史改动

必须覆盖真实形状：

- 手机发起的 live turn；
- Desktop 发起的 live turn；
- app-server 重建历史；
- 原始 rollout 补充；
- 完整 Mirror 下载；
- old Bridge fallback；
- 重连和延迟帧；
- 父子 Fork；
- 大会话和远距离分页。

### UI 与动画

- 自动测试防结构、几何、生命周期和性能回归；
- 安装或打开最新构建，确认实际运行的是目标 worktree 产物；
- 由用户完成动态手感、布局和视觉验收。

如果用户说“没有看到”或“还是不对”，立即撤回完成结论，先核对当前安装包、源码、运行进程和真实会话，不用单测结果反驳用户。

## 16. 运行服务的安全规则

- “可以发现但连不上”不等于一定有两个 Bridge；分别检查进程数、端口、WebSocket、Tailscale、代理路由和协议版本。
- 不在依赖当前 Bridge 连接的会话里直接执行会 unload 自己的 setup/reinstall。
- 重载全局服务前备份 plist/配置并保留回滚记录。
- 服务启动输出不是健康证明；至少核对正确入口、唯一进程、listener、HTTP/WebSocket 握手和手机目标地址。
- 官方 Bridge、compat Bridge 和测试 Bridge 必须区分；测试默认使用独立端口，不能抢占用户正在使用的实例。
- 不用 `ps eww` 等可能打印凭据的方式诊断进程。

## 17. 安全、隐私与许可证

- API key、Shorebird token、RSA 私钥、provisioning 内容和 Firebase 凭据不得进入 Git、日志、截图或交接文档。
- 文件、artifact、Mirror、通知和调试 bundle 遵循最小内容原则；能传 opaque ID 就不传正文或绝对路径。
- 预览和文件服务必须认证、限制目录、限制大小、支持取消，并防止 symlink/path traversal。
- 不通过 Bridge 下发可执行代码。
- 本地 fork 按 GPL-2.0-only 维护；上游 MIT notice 保留。引入或改编第三方实现前先确认许可证，保留 SPDX、原作者 notice 和 `THIRD_PARTY_NOTICES.md`。
- 网络位于局域网或 tailnet 只降低暴露面，不消除认证和访问控制要求。

## 18. 与用户沟通

- 使用中文，先说结论，再给必要证据。
- 不把计划、截图、代码存在、测试或构建中的任何一个单独包装成最终完成。
- 用户明确指定先后顺序时严格遵守；流程纠正会改变后续做法，但不等于自动停工。
- 用户说“先把 IPA 给我”时，先交付 IPA，再把签名、安装、JIT 和真机启动列为独立后续门禁。
- 视觉检查由用户负责时，准备好最新构建后直接告诉用户如何复现，不继续进行昂贵的伪视觉验收。
- 不反复询问可以从源码、运行状态或现有决策中查明的问题。
- 风险存在时具体说明影响、证据和剩余验证，不笼统说“应该没问题”。

## 19. Agent 完成回报模板

每个独立任务结束时至少回报：

1. 任务目标和实际完成范围；
2. 仓库、绝对 worktree、分支和起始基线；
3. 所有 commit 完整 SHA、顺序和依赖；
4. `git status --short`，以及未提交或不属于自己的改动；
5. 关键文件、行为 owner 和协议/数据边界；
6. 实际执行的测试、构建、运行验证及原始通过/失败信号；
7. 未做的真机、视觉、部署、签名或发布门禁；
8. 旧/新 Mobile、Bridge、native host、协议和存储的兼容性；
9. 与官方上游的基线、偏离热点和建议语义合并顺序；
10. 是否需要新基础 IPA、Bridge 部署、owner OTA 或 stable 明确批准。

回报前不要自行 merge、push、rebase、发布、清理分支或删除 worktree。

## 20. “完成”的定义

只有同时满足以下条件，代码任务才能称为完成：

- 用户要求的行为已实现，没有用缩小需求或数据上限绕过；
- 权威来源、身份和兼容边界正确；
- 相关自动测试和构建通过；
- 工作树只含本任务改动，提交粒度可审查；
- 旧版本 fallback 已验证或明确限制；
- 需要用户目检的内容已经交给用户验收，不能自行代替；
- 需要真机、签名、部署或 stable 批准的任务没有被误报成已完成；
- 协调 Agent 已收到完整回报。

当其中一项仍未完成时，使用“代码完成、待真机”“已构建、未安装”“owner 已发布、stable 未晋级”等精确表述。
