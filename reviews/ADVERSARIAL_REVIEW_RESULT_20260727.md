### [P1] Trimmed context diff breaks fingerprint-path apply for hunks ending the file's diff

- 位置：`packages/bridge/src/git-operations.ts:297`，commit `403ad9f6`，维度 git-contract
- **主张**：The new fingerprint path fetches the default-context diff via the git() helper whose .trim() strips the diff's trailing whitespace, so buildFingerprintPatch emits a patch whose last hunk is missing/mangling its final line whenever that line is whitespace-only or ends in \r or trailing spaces, making stage/unstage/revert of that hunk fail where the legacy --unified=0 index path succeeded.
- **场景**：Verified with real git: commit a file 'l1\nl2\nl3\nl4\nl5\n\n' (trailing blank line), edit l3->l3x in the worktree, tap stage on the single displayed hunk from a new app. The displayed diff's last trailing-context line is ' ' (blank source line); git()'s .trim() deletes it from the re-run diff, the built patch is one line short of the @@ header count, and 'git apply --cached' fails with 'error: corrupt patch at line 12' — the baseline legacy U0 path stages this exact change correctly, so this is a regression for new clients. Same root cause on CRLF files: the final context line loses its \r and every stage/unstage/revert of the file's last hunk fails with 'patch does not apply'; and when the diff ends in a change line with trailing whitespace/\r, the Bridge hashes the trimmed line so the fingerprint check permanently rejects with 'The file changed since the diff was displayed; refresh and retry' even though nothing changed and refreshing never helps. All failures are fail-closed (git apply is atomic, no tree corruption), but hunk-level git operations become unusable for these common inputs. Fix: don't trim the context diff (or re-append the stripped trailing line), e.g. use untrimmed stdout for contextDiffArgs in applyHunks (git-operations.ts:297, helper at :122-127, patch assembly at :163-215).
- **核实**：I attempted to refute the claim but instead confirmed it by end-to-end reproduction with real git and the actual shipped code. Steps: (1) Created a repo in the scratchpad, committed f.txt = 'l1\nl2\nl3\nl4\nl5\n\n' (trailing blank line), edited l3->l3x. `git -c core.quotePath=false diff --no-color -- f.txt` verified via od -c to end with ' l5\n \n' — the final trailing-context line for blank line 6 is a single space. (2) Imported the real `stageHunks` from packages/bridge/src/git-operations.ts via the repo's tsx and called it with the fingerprint a new client would send ({oldStart:1, oldLines:6, newStart:1, newLines:6, changesHash: hashHunkChangeLines(["-l3","+l3x"])}). Result: `git apply --cached -` failed with 'error: corrupt patch at line 12' — the exact error the reviewer predicted. Mechanism confirmed in code: the fingerprint branch of applyHunks (git-operations.ts:280, :297) fetches the default-context diff through the `git()` helper whose `.trim()` (git-operations.ts:126) strips the trailing ' \n', deleting the whitespace-only final context line; buildFingerprintPatch (:163-216) still passes the fingerprint check (header quadruple and +/- change lines are untouched) and emits a patch one line short of its @@ -1,6 +1,6 header count, which git apply rejects. (3) Called the same `stageHunks` with only hunkIndex (legacy path, the only behavior at baseline): it staged the change successfully. (4) Checked baseline 20382de6 (git show of git-operations.ts): the `.trim()` existed, but all three applyHunks callers (stageHunks/unstageHunks/revertHunks) used only `--unified=0` diffs, which contain no context lines, so a whitespace-only final line essentially cannot occur there — the exposure of the trim to default-context diffs is introduced solely by commit 403ad9f6 (the only commit touching this file since baseline). Therefore this is a genuine regression introduced by the remediation: for new clients (which now send fingerprints per the same commit's git_view_cubit.dart change), stage/unstage/revert of any hunk whose last displayed context line is blank (a very common case: files with a trailing blank line, or blank lines within trailing context) fails closed with a git apply error, where old clients/baseline succeed. The failure is fail-closed (no tree corruption), and the CRLF/hash-mismatch sub-scenarios share the same root cause (I did not separately reproduce those; the primary scenario alone confirms the defect). Fix as suggested: use untrimmed stdout for the contextDiffArgs fetch in applyHunks (git-operations.ts:297) or restore the stripped trailing content before parsing.

- **场景**：Old Bridge (rejects get_history_delta), session with non-empty runtime store: reconciliation -> delta rejected -> _fallbackPendingHistoryDeltaRequests records fence gen5 and sends get_history -> Bridge hits a transient error (e.g. Codex rollout read failure or a throw in the past-history split) and sends only an error frame -> fence gen5 leaks. - **核实**：Attempted refutation failed on every link. (2) Client-side leak confirmed: fences are popped only in _acceptLegacyHistoryFrame (bridge_service.dart:3645-3669), invoked only for HistoryMessage (lines 1523-1524); the ErrorMessage handler (1872-1890) never pops a fence, no timeout clears them, and clears happen only on (re)connect (1419) or bridge switch (2059). (3) Bridge-side error-only get_history answers are real and untouched by the branch: session_not_found (websocket.ts:6681-6687) sends only an error; sendCodexCanonicalLegacyHistory's catch (websocket.ts:2976-2984) sends only an error yet returns handled=true so no history frame follows; a throw in splitPastHistoryMessages reaches the fire-and-forget void handleClientMessage(...).catch at websocket.ts:3790 which only logs and sends nothing. The only weakness is that the repo history is squashed at Bridge v1.105.0+187 so a genuinely pre-delta Bridge could not be inspected directly, but the session_not_found error-only shape exists at the earliest visible commit and the codebase/docs treat pre-delta Bridges as live deployment targets; the empty-store early-accept (line 3654) does not rescue the scenario because it stipulates a non-empty runtime store. The claim stands as a genuine defect introduced by these changes.

### [P2] Old-Bridge full-history fallback response rejected by any interleaved session frame, with no retry

- 位置：`/Users/huyiyang/AI agent/Codex/_keep/projects/ccpocket-worktrees/mobile-comprehensive-remediation-20260725/apps/mobile/lib/services/bridge_service.dart:3668`，commit `7c3fca5f`，维度 dart-state

- **核实**：I attempted to refute the claim and failed — every link of the chain is concretely reproducible in the code, and the behavior is new in commit 7c3fca5f (at baseline 20382de6 a `history` frame was applied unconditionally; the fence, `_acceptLegacyHistoryFrame`, and the drop path do not exist there).

### [P2] Origin-gate rejects the repo's own Flutter Web client, contradicting the zero-compat-cost claim

### [P2] History fence drops superset Claude frames on old Bridges, leaving reconnect gaps unhealed

- 位置：`apps/mobile/lib/services/bridge_service.dart:3668`，commit `7c3fca5f`，维度 protocol-compat
- **主张**：The contentEpoch equality check rejects any full-history frame that raced a live message, but for Claude sessions the Bridge builds the frame from in-memory session.history on the same FIFO socket, so any live message the client applied before the frame is necessarily contained in the frame — the fence rejects frames that would not destroy newer state, contradicting the commit's 'old-Bridge fallbacks behave as before' and 'only rejects frames that would destroy strictly newer state' claims.
- **场景**：Old Bridge (get_history_delta answers unsupported_message, so every sync uses fenced legacy get_history) + active Claude session: the socket drops mid-turn and reconnects; the runtime store is retained (only fences are cleared), so messages emitted during the outage are missing. The foreground sync records a fence with contentEpoch E; the agent is still streaming, an assistant/tool_result message lands during the request round-trip bumping the epoch, and the returned full frame — which contains both the racing message and the outage-gap messages — is dropped. The gap the baseline behavior would have healed stays visible until some later sync happens to complete without a racing message.
- **核实**：Attempted refutation failed; every premise of the claim verifies against the actual code. (1) The fence is wholly new in commit 7c3fca5f — at baseline 20382de6 bridge_service.dart has no _acceptLegacyHistoryFrame, so a legacy history frame was always applied and healed reconnect gaps. (2) Old-Bridge fallback is fenced: unsupported_message for get_history_delta (bridge_service.dart:1873-1876) invokes _fallbackPendingHistoryDeltaRequests (2248-2265) which records a fence (contentEpoch=E, storeWasEmpty=false; 3626-3637) and sends get_history. (3) A same-bridge reconnect retains the runtime store while clearing fences: connect() clears _pendingLegacyHistoryFences (1417-1419) but _runtimeStore.clearAll() (2069) runs only on isBridgeSwitch (1432-1434), so messages emitted during the outage are missing from a non-empty store. (4) Reconnect triggers the fenced sync: claude_session_screen.dart:984-990 calls refreshHistory() on BridgeConnectionState.connected. (5) Any non-ignored live message (assistant, tool_result, permission_request, status) applied at bridge_service.dart:1543 bumps contentEpoch (session_runtime_store.dart:100), so a message landing during the delta-error→get_history→frame round trip (realistic mid-turn over Tailscale) makes line 3668 (snapshot.contentEpoch == fence.contentEpoch) false and the frame is dropped (1523-1531) with the sync lifecycle completed and no retry (2240-2246; the reconciliation stream is only a completion signal for background_sync_coordinator). (6) The claim's FIFO-superset premise holds for Claude sessions: session.ts appends historyMsg to session.history (line 1125) before broadcasting (line 1129), and websocket.ts builds the history frame by spreading session.history at send time (6659-6663); WebSocket FIFO therefore guarantees any live message the client applied before the frame is contained in the frame, along with the outage-gap messages the client never received. Applying the frame would destroy no newer state and would heal the gap; rejecting it leaves the gap visible until some later sync completes without a racing message — a strict regression versus baseline, contradicting the commit's stated invariants ('old-Bridge fallbacks behave as before', 'only rejects frames that would destroy strictly newer state'). The commit's own regression test constructs a stale frame that omits the racing live message — a frame shape a Claude-session Bridge cannot produce on one FIFO socket — so the test does not contradict this finding. The defect is real, introduced by these changes, and not pre-existing.

## 反驳的主张（不修）

### uncaughtException continue replaces launchd self-healing restart with a wedged process
- The claim's concrete failure scenario does not reproduce. (1) Its flagship example — a TypeError in a ws 'message' handler mid-way through appending session history — cannot reach the new uncaughtException guard and never crashed at baseline: the entire client-message pipeline runs inside async handleClientMessage, invoked as `void this.handleClientMessage(msg, ws).catch(...)` which logs and continues, and that exact .catch exists verbatim at baseline 20382de6 (websocket.ts:3746ff; current websocket.ts:3790). The sync prefix (parseClientMessage/JSON.parse) is try/catch-wrapped. So the "before: crash + launchd restart / after: continue with half-mutated state" contrast is false for that path — log-and-continue there is pre-existing. (2) The session output→history→broadcast pipeline is driven by async SDK iteration (for await in sdk-process.ts), so throws there become promise rejections handled by the unhandledRejection guard that the claim itself endorses as the correct fix — identical continue-with-partial-state semantics regardless of the disputed handler. (3) The "timer callback" limb names no actual unguarded throwing site; the one identified timer-driven sync fan-out (catalog-monitor debounce) was explicitly isolated with per-handler try/catch in commit 3d41f260 on this same branch (local-features/controller.ts:105-118). The uncaughtException handler only ever fires when some other, unspecified defect exists, making the scenario hypothetical. (4) What remains is a design disagreement, not an introduced defect: the commit message explicitly documents both guards and the log-and-continue choice ("注册 unhandledRejection / uncaughtException 兜底，记录后继续服务不退出"); a Bridge exit kills every active Claude/Codex CLI child session (aborting all in-flight runs for all clients — the failure mode the remediation targets), launchd KeepAlive is only one of several documented deployments (npm run bridge / menubar spawn have no supervisor), and KeepAlive still covers genuine exits. Baseline facts in the claim are accurate (no uncaughtException handler at 20382de6; plist:38 and setup-launchd.ts:226 set KeepAlive=true), but with no concrete unguarded sync-throw path demonstrated, the alleged regression is a deliberate, logged, last-resort availability tradeoff rather than a genuine defect introduced by the change.

### Background delta-only request invalidates an in-flight legacy history response it cannot replace
- The scenario's triggering step is unreachable on an old Bridge, and its "nothing re-fetches" tail is false even in the contrived mixed case.

1) The gen6 bump cannot happen in the claimed scenario. `requestSessionHistoryDeltaOnly` has exactly one production caller: `BridgeServiceBackgroundSyncGateway.requestSessionHistory(allowFullFallback: false)` at apps/mobile/lib/features/background_sync/background_sync_coordinator.dart:116. The coordinator only reaches that call for sessions passing the filter at lines 625-630 of the same file: `foreground || _bridge.hasCachedSessionHistory(sessionId)`. For background triggers (enteringBackground/appRefresh) foreground=false, so the session must satisfy `hasCachedSessionHistory` = `cachedSessionHistorySeq(sessionId) > 0` (lines 121-122). But on an old Bridge - by the claim's own definition, one that answers get_history_delta with unsupported_message - `cachedHistorySeq` can never become nonzero: per apps/mobile/lib/services/session_runtime_store.dart (lines 101-157) it is set only by HistorySnapshotMessage.toSeq, HistoryDeltaMessage merges, or live frames stamped with `historySeq` - all parts of the same seq-sync protocol as get_history_delta (implemented together in packages/bridge/src/websocket.ts). Moreover, any applied legacy `history` frame explicitly resets `cachedHistorySeq` to 0 (session_runtime_store.dart:109), so a store populated via the legacy path (the claim's premise: "old Bridge, non-empty store") necessarily has seq == 0. Therefore the backgrounding coordinator filters the session out, requestSessionHistoryDeltaOnly is never invoked, the generation stays at gen5, and the in-flight legacy frame's fence (gen5) matches at bridge_service.dart:3658 - the frame is accepted, not dropped.

2) Even in the only conceivable variant where cachedHistorySeq > 0 (the Bridge downgraded/replaced mid-app-run after a seq-synced store was built), the claim's consequence is overstated: (a) dropping a legacy full frame over a seq-synced store is the intended protection - applying it would wholesale-replace the store and zero the watermark (the exact baseline bug commit 7c3fca5f fixes); (b) the dropped frame still fires `_emitSessionHistoryReconciliation` (bridge_service.dart:1529), so the sync lifecycle completes without hanging; and (c) "nothing else re-fetches" is wrong - entering background sets `_foregroundCatchupPending = true` (background_sync_coordinator.dart:241), which forces a `_synchronize(resumed)` with foreground=true on the very next foreground transition, calling `requestSessionHistory` with full get_history fallback. The staleness window covers only time the app is backgrounded and nothing is rendered; the guaranteed foreground catch-up heals it before the user can observe stale history.

3) Additionally, the claimed message ordering is implausible: the fallback get_history is sent before backgrounding, while the coordinator must first complete a fresh list_sessions round-trip (waiting for authoritativeSessionListGeneration to advance, coordinator lines 758-773) before issuing any delta-only request; on the single ordered WebSocket an old Bridge answers get_history before that session_list, so the history frame arrives while the generation is still gen5.

No caller other than the coordinator reaches the allowFullFallback:false path (verified by grep across apps/mobile/lib). The claimed defect scenario cannot be reproduced from the actual code.

### Legacy history fence FIFO desyncs permanently when get_history is answered by an error frame
- The claim's code-level mechanism is accurate but its failure scenario cannot occur. Verified in apps/mobile/lib/services/bridge_service.dart: fences are popped only by HistoryMessage frames (line 1523), the ErrorMessage handler (lines 1872-1891) and sync timeouts do no fence cleanup, and fences are cleared only on connect()/bridge-switch — so an error-only get_history reply would leave a stuck fence and desync the FIFO exactly as described. However, the scenario's two preconditions are mutually exclusive across real Bridge versions: packages/bridge/CHANGELOG.md shows get_history_delta was added in 1.47.0 (2026-04-28) while the Codex canonical thread-read path (sendCodexCanonicalLegacyHistory, the only error-only reply for a FOUND session, websocket.ts ~2976 catch) arrived in 1.63.2 (2026-05-30). A delta-unsupported Bridge (pre-1.47) serves get_history from in-memory session.history and always sends a history frame; any Bridge that can hit a "transient rollout read error" supports get_history_delta, so the perpetual legacy fallback via line 2259 (triggered only by unsupported_message/get_history_delta) never runs against it. Against delta-supporting Bridges the app sends get_history only when the store is empty (line 3615; the only two senders, lines 2260 and 3617, both record fences), and a stuck fence is then harmless: later legacy frames are accepted by the empty-store early return (line 3654) regardless of pairing, and once the store is populated sync uses history_delta/history_snapshot (lines 1514-1520) which bypass the fence — worst case a one-shot race-window drop followed by delta recovery, not the claimed persistent loop. The session_not_found trigger (~6681) strands a fence for a session the Bridge no longer has, so no further history frames arrive to be mis-paired; sustained harm would need the same bridge session id reborn on the same socket with a non-empty store, but stopped-session handling calls clearExplorerHistory -> _runtimeStore.clearSession (line 3914), emptying the store and re-enabling unconditional accept — no concrete reachable chain exists. The Bridge's error-only reply paths are baseline behavior untouched by the remediation diff. The missing error-path fence cleanup is a latent fragility, but the claimed user-visible sustained failure is not reachable.
